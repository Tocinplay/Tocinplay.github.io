这次折腾的目标，是把手上的 MF601SL 随身 Wi-Fi 变成一台常驻的小服务器：实体 SIM 卡负责接收短信，设备通过家里的 Wi-Fi 联网，再把短信转发到手机上的 Bark。同时，我希望能在网页里查看系统状态、管理网络和服务，并在 Wi-Fi 失联时通过 USB 数据线救回来。

最终选择了 Debian，没有继续配置 OpenWrt 或旁路由。这篇文章记录本机的实现过程和实际验证结果，不是一份适用于所有同名设备的一键刷机教程。刷机包、板型、设备树和基带文件需要分别核对，软件界面显示“安装完成”也不能替代开机和通信测试。

## 最后装了什么

| 功能 | 本次方案 | 验证情况 |
| --- | --- | --- |
| 系统 | Debian 12，ARM64，社区 6.4 内核 | 可以启动并运行服务 |
| 实体 SIM | ModemManager 管理基带 | SIM 识别、网络注册正常 |
| 短信转发 | sms-relayed + Bark | 配置已启用，Bark 测试推送成功；真实新短信的完整转发链路仍待测试 |
| 网页管理 | Cockpit + 自定义设备与网络页面 | 服务、接口和页面文件已验证 |
| 远程访问 | 原生 Tailscale 服务 | 已加入账号，设备间连接成功 |
| USB 备用访问 | RNDIS 网络 + ADB | Windows 驱动正常，两个后台实际访问成功 |
| 容器 | Docker | ARM64 BusyBox 导入、运行和基本管理成功 |
| 流量统计 | vnStat | 已记录 Wi-Fi 与蜂窝接口流量 |
| 网络唤醒 | 自定义页面发送 WOL 包 | 数据包格式已验证，未测试实际唤醒电脑 |

我的核心原则是：**关闭蜂窝数据自动连接，保留 SIM 的网络注册，用 Wi-Fi 承担服务器的联网流量。** 注册到移动网络与建立互联网数据连接是不同的状态。设备可以显示 LTE、运营商和漫游注册，同时保持数据连接关闭。

## 一、先让系统、基带和实体卡正常工作

我使用的是酷安作者 jsbsbxjxh66 提供的 Debian 方案。可以参考[作者的分享页面](https://www.coolapk.com/feed/41664623)，以及 [OpenStick 项目文档](https://www.kancloud.cn/handsomehacker/openstick/2636506)。镜像与板型是否匹配，需要以自己的设备为准。

刷入系统只是起点。接下来至少要分别确认：USB 能否枚举、ADB 或 SSH 能否进入、Wi-Fi 是否启动、调制解调器是否出现、SIM 是否正确、运营商是否注册。不能把“能进 Debian”直接当作“短信服务器已经可用”。

这台设备同时存在内置 SIM 与实体卡槽，因此还需要确认当前读取的卡确实是插入的实体卡。我通过 SIM 信息与实际卡片核对，而不是只看“检测到 SIM”这一条状态。

`modem.mdt` 也不是单独拿来替换就能保证通信正常的万能文件。实际基带加载还涉及对应的分段固件、引导文件和板级配置。本机最后使用了核对过的原厂基带文件，并检查 ModemManager 是否能够发现设备。设备身份、校准数据和固件兼容性都应单独处理，不能把另一台机器的备份当成通用恢复包。

日常检查可以从下面几条只读命令开始：

```bash
mmcli -L
mmcli -m 0
ip route
nmcli connection show --active
```

其中 `0` 是当前检测到的调制解调器编号，重启或恢复后可能变化，需要先看 `mmcli -L` 的结果。

## 二、让设备连 Wi-Fi，不自动使用 SIM 流量

我删除了镜像默认创建的热点连接，把设备改成 Wi-Fi 客户端，连接家里的无线网络，并启用该连接的自动连接。

这里有一个很容易踩的坑：如果正在通过热点访问设备，直接删除热点就会切断自己的管理入口。切换网络之前，最好先准备好 USB 网络或 ADB，再确认新 Wi-Fi 能够连接。

SIM 数据连接的自动连接保持关闭。不能只看运营商已注册就判断设备在用流量，需要同时查看活动连接、数据承载与默认路由。本机正常情况下，默认路由走 `wlan0`，蜂窝连接处于断开状态。

数据漫游开关也不等于禁止漫游注册。对漫游 SIM 来说，完全禁止注册会影响通信；我关注的是是否允许建立漫游数据连接，并保持数据自动连接关闭。

## 三、用 sms-relayed 转发到 Bark

短信部分使用 [sms-relayed](https://github.com/frankwei98/sms-relayed)。它通过 ModemManager 的 D-Bus 接口处理短信，提供 Web 管理界面，并支持 Bark 等通知渠道。

本次安装使用了本地下载的 ARM64 发布文件，先核对对应 SHA-256，再导入设备。这样也绕过了设备直接下载速度慢的问题。安装后用 systemd 管理服务，配置文件放在 `/etc/sms-relayed/config.toml`。

在 Web 后台填写自己的 Bark 服务器地址和设备密钥，启用转发配置，再发送测试推送。本机的 Bark 测试已经成功，但这只验证了设备到 Bark 的通知通路，不能证明 SIM 接收新短信、入库、触发转发这一整条链路都通过了测试。

因此我保留了一个明确的验收项目：从另一部手机给这张 SIM 发送普通短信，检查后台记录和 Bark 到达情况。公开文章中不保存真实 Bark 密钥、管理密码、短信内容或验证码。

服务和调制解调器的基础健康状态可通过下面的接口查看：

```bash
curl http://127.0.0.1:8080/api/health
```

两项均显示正常，只代表基础服务可用；最终仍应做真实收信测试。

## 四、用 Cockpit 管理这台小服务器

系统管理面板选择了 [Cockpit](https://cockpit-project.org/)。本次以基础系统管理组件为主，提供状态、服务、日志和终端，并创建了独立管理账号。

我另外添加了“设备与网络”页面，集中放置 Wi-Fi、SIM 数据设置、流量统计、网络唤醒和 Docker 管理。这里的专用功能来自本次自定义扩展，不能把它们理解成安装基础 Cockpit 后默认就全部拥有。

修改 Wi-Fi 时，页面使用延迟执行与限时确认：修改后需要确认保留，超时则恢复原连接。本机已经测试过一次真实的回滚流程；切换到另一条 Wi-Fi 和热点模式尚未逐项实测。

如果页面提示 `Not permitted to perform this action`，先检查是否启用了 Cockpit 管理权限，以及输入的是当前管理账号的密码。查看状态和执行网络修改需要的权限不同，不能为了省事直接给整个后台开放免密码管理权限。

为了直接输入 IP 就能打开面板，我增加了一个 **80 端口跳转入口**。访问 `http://设备IP/` 时，会自动跳转到原来的 `https://设备IP:9090/`。面板登录仍使用 HTTPS，80 端口不承担明文登录。

## 五、Tailscale 负责远程访问

最初考虑过 DDNSTO，后来改用 Tailscale。本次在 Debian 里直接安装原生服务，绑定自己的账号，并设置开机启动。客户端也要登录同一个账号，才能通过 Tailscale 地址访问设备。

我没有让这台小机器承担出口节点或子网路由，也没有配置旁路由。用途就是远程访问它自己的管理面板、短信后台和 SSH。

可以用下面的命令检查状态：

```bash
tailscale status
tailscale ip -4
systemctl is-enabled tailscaled
```

拿到设备的 Tailscale IP 后，访问方式是：

```text
服务器面板：http://设备的Tailscale-IP/
短信后台：http://设备的Tailscale-IP:8080/
```

本机已经验证 Tailscale 在线、设备间通信，以及服务在 Tailscale 地址上的响应。手机离开家里的网络后访问，是另一项需要单独验证的场景。

长期无人值守还要关注设备密钥到期。可信的常驻设备可以在管理控制台选择关闭该设备的密钥过期；这是账号侧设置，与 Linux 服务是否开机启动是两回事。参见 [Tailscale Linux 安装与维护说明](https://tailscale.com/docs/install/linux)。

## 六、RNDIS 是 Wi-Fi 失联时的备用入口

我希望即使 Wi-Fi 地址失联，也能插上数据线管理设备。这需要设备提供 USB 网络接口，同时让 Windows 正确识别对应驱动。

本机最终使用 Windows 自带的微软 RNDIS 驱动，没有安装来源不明的驱动包，也没有关闭驱动签名验证。微软提供并维护 RNDIS 驱动，详见 [Remote NDIS 官方说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/remote-ndis--rndis-2)。

我遇到的关键问题是：Windows 把整个 USB 父设备绑定成了 ADB，导致网卡子接口无法正常出现。正确结构应该是一个 USB Composite Device 父设备，下方分别是 RNDIS 网络接口和 ADB 接口。给父设备安装 ADB，与给 ADB 子接口安装驱动，是两件不同的事。

本次补齐了 USB 的 RNDIS 兼容描述符，并调整接口标识，使 Windows 能分别匹配复合设备、网卡与 ADB。相关配置写入设备的 USB 启动脚本。

连接成功后，设备的 USB 地址是 `10.42.0.1`，电脑自动取得同网段地址。管理入口如下：

| 用途 | USB 直连地址 |
| --- | --- |
| 服务器面板 | `http://10.42.0.1/`，自动跳转 HTTPS |
| 短信后台 | `http://10.42.0.1:8080/` |
| SSH | `ssh 管理账号@10.42.0.1` |

这些地址已经从 Windows 通过 USB 实际访问成功，ADB 同时可用。电脑上的 USB 网卡 IPv4 路由优先级设得比原有网卡低，避免插线后抢占原来的上网连接。

最后一次 USB 配置已持久保存，但尚未再次完整冷启动验证。USB 可以解决 Wi-Fi 失联的问题，不能解决设备断电或内核卡死的问题。

## 七、小内存设备上的 Docker、交换空间和网络唤醒

这台设备可用内存总量约 372 MiB，不适合堆叠很多后台服务。本次保留原有约 186 MiB 的 ZRAM，没有直接运行额外的交换文件脚本。是否需要更多交换空间，应看真实负载下的可用内存和交换使用情况。

Docker 已安装并设置启动，但只验证了轻量 ARM64 容器。镜像拉取遇到网络问题时，我使用本地下载、校验、导入的方式进行测试，并限制容器日志大小。容器能运行，不代表机器适合长期承载多个大型应用。

vnStat 用来统计接口流量。它记录的是经过接口的数据量，不能当作运营商剩余套餐的查询结果。

网络唤醒页面可以保存电脑的 MAC 地址和广播地址，再发送 WOL 数据包。目前只验证了数据包格式，尚未验证实际电脑能否被唤醒。电脑端仍需要网卡、固件和电源状态配合。远程使用时，可以先通过 Tailscale 打开这台设备的面板，再由设备在局域网内发送唤醒包。

## 八、VoLTE 和主动拨号还没有完成验证

短信后台出现“调制解调器未提供 IMS 服务／注册／设置查询接口”的提示，并不等于已经确认不支持 VoLTE，也不表示短信一定不能工作。它说明当前查询无法取得这些信息。

本机的 ModemManager 暴露了语音控制接口，QMI 语音配置查询也成功，但尚未做实际外呼测试。当前网络模式是仅 4G，不能依靠回落到 2G/3G 来验证传统语音通话。

另外，Debian 当前没有识别到声卡，也没有打通通话音频路径。即使以后能够拨号并让对方响铃，也不能直接推导出可以双向说话或播放录音。VoLTE、拨号接通和音频通路需要分别验证。

## 九、开机自启与稳定性是两个问题

本次已经检查了 Wi-Fi、USB 配置、短信服务、Cockpit、80 端口入口、Tailscale、Docker、流量统计与恢复服务的启动设置。蜂窝数据自动连接保持关闭。

可以用下面的命令复查主要入口：

```bash
systemctl is-enabled NetworkManager linux-adbd-utils sms-relayed cockpit.socket tailscaled
systemctl is-active NetworkManager linux-adbd-utils sms-relayed cockpit.socket tailscaled
```

折腾期间，这台设备出现过多次 USB 与 Wi-Fi 同时消失，也曾出现非法指令和内核 CPU 卡顿。完整断电后可以恢复，但目前不能断言根因是供电、温度、硬件、固件还是内核。

另外，基带在开机异常恢复后可能处于“处理器运行、但 ModemManager 找不到调制解调器”的状态。我加入了启动时的一次恢复检查，本机手动恢复已经成功；新增恢复逻辑仍需要后续冷启动验证。它是针对本机故障现象的处理，不应直接复制到其他机型。

现在已经得到一台可以管理、可以远程访问、也有 USB 备用入口的小服务器。接下来最有价值的工作，是完成真实短信转发测试、冷启动检查和长时间稳定性观察，再决定是否继续折腾语音功能。
